# 当前 TPS 预测的真实验证（2026-11-14）

## 结论

**这次五阶段均值比较接近，但模型内部还没有预测准，不能用 1.87% 的总误差证明配置排名可靠。**

- 预测在执行完整 AP SQL 之前冻结，没有用目标 TPS 回填。
- 实际跑完 TP128 → TP128+16、原始 SF85 AP SQL 的连续五阶段；
  每阶段 3 个 15 秒同步 commit/device 窗口。
- 阶段等权 MAPE **1.868%**；15 个窗口等权 MAPE **2.614%**。
- S5 均值低估 **5.282%**；S4 的同阶段波动没有被单一平均资源需求刻画。
- 查出并修复一个确定的采集错误：**原来只统计 `runuser` 外壳，漏记 Sysbench 工作线程的 CPU**。
  修复后 TP-only 短实测检出了约 **1.141 个 CPU 核**的客户端开销，外壳旧口径为 0。
- 这是测量链修复，不是“已重新训练并通过留出测试的新 TPS 模型”。原始预测完整保留。

入口：`CURRENT_CAPACITY_TPS_VALIDATION.json`。
证据目录：`results/capacity_TPS_validation_20261114_1957/`。

## 1. 本次到底执行了什么

| 阶段 | 运行中的 AP | SB (GiB) | TP |
|---|---|---:|---|
| S1 | Q18 | 5 | 128 |
| S2 | Q18、Q21 | 5 | 128 |
| S3 | Q18、Q21、Q9、Q13 | 5.25 | 128 |
| S4 | 再加入 Q2 | 5.25 | 128 |
| S5 | Q2 离开，其余继续 | 5.25 | 保留原128，新增16在首个计分窗口开始时放行 |

WM 全程固定：Q2=32、Q9=512、Q13=128、Q18=1024、Q21=512 MiB。
这是用于准确率诊断的较保守固定控制，不是创新三刚求出的最优 WM，不能冒充推荐配置验证。
SB 取自上一轮基数/历史 AP 驻留情景的 256 MiB 分辨率验证候选。

AP 是完整原始查询，不是 LIMIT/简化代理查询；SQL SHA、WM、实际 SB、TP 后端集合和
S5 首事件门控均核对。AP 在阶段间持续运行。每阶段三个窗口不是三个独立生命周期重跑。
结束时按计划只取消本实验 AP；不把取消运行当作完整 AP 时间、spill 或算子真实行数标签。

原有 TP-only 缓存拟合域为 512–4096 MiB。本次通过独立的实验性桥接明确声明：
AP 驻留是 TP 容量损失的代理；高于已校准域的有效 TP 容量使用 4 GiB 平尾假设。
没有扩大原拟合域、没有关闭严格混合负载排名拒绝门。

## 2. 冻结预测与实测 TPS

误差定义为 `(预测 / 实测 - 1)`；实测均值由对应同步窗口的 commit 总数 / 总秒数计算。

| 阶段 | 开跑前预测 | 三窗口实测 TPS | 实测均值 | 相对误差 |
|---|---:|---|---:|---:|
| S1 | 7430.55 | 7578.60 / 7507.33 / 7586.40 | 7557.44 | -1.68% |
| S2 | 7460.07 | 7535.87 / 7499.67 / 7448.67 | 7494.73 | -0.46% |
| S3 | 7396.70 | 7457.40 / 7289.87 / 7148.60 | 7298.62 | +1.34% |
| S4 | 7411.61 | 7063.47 / 7294.67 / 7749.87 | 7369.33 | +0.57% |
| S5 | 7314.21 | 7688.80 / 7775.27 / 7702.20 | 7722.09 | -5.28% |

特别是 S4，均值误差只有 0.57%，但内部 TPS 范围约 686；“均值接近”并不代表能预测波动。
S4→S5 模型预测下降，实际本次轨迹上升；AP 所处资源阶段和 TP 负载拓扑不能仅由活跃 query 数决定。

## 3. 不准发生在哪一层

### 3.1 TP-only 基线迁移偏低

在 AP 启动前先做了同口径 TP128 对照：

| SB | 旧模型的 TP-only 基线 | 本次 TP-only 对照 | 模型偏差 |
|---|---:|---:|---:|
| 5 GiB | 约7561.83 | 7847.40 | -3.64% |
| 5.25 GiB | 约7561.83 | 7994.00 | -5.41% |

每个控制点只有一个15秒窗口，不足以据此重新确定 SB 排序。两点的时间、缓存历史不同，
不能把其差值全部解释成 SB 增益。这里能确认的是：旧 TP 成本校准直接迁移到本次环境有偏差。
S5 没有本轮同口径 TP-only 128+16 对照，**没有**用平144或比例缩放TP128冒充真值。

### 3.2 AP 干扰也低估，部分抵消了低基线

例如 S3，模型自身基线到混跑的下降只有 **165.14 TPS**；
本次 5.25 GiB TP128 对照到 S3 均值的差为 **695.38 TPS**。
这个对照差不是严格随机化的 AP 因果效应，但足以提示：
总 TPS 误差 1.34% 并不意味着 AP 干扰预测同样准确。

AP CPU 需求的对照：

| 阶段 | 模型：media closure 后平均核数 | 实测：活跃窗口 AP CPU 核数 |
|---|---:|---:|
| S1 | 0.501 | 0.568 |
| S2 | 0.389 | 0.626 |
| S3 | 0.597 | 0.975 |
| S4 | 0.539 | 0.784 |
| S5 | 0.599 | 0.391 |

CPU 用 `/proc/.../schedstat` 自己的采样区间归一化，不把不同区间强行缩放成真值。
本轮端点100ms检查全部通过，但仍不是精确到 commit 内核窗口的事件 CPU 归属。
模型是全查询平均资源比，实测是查询执行到当前时刻的活跃段；二者不一致正是需要补的阶段化桥接。
没有本轮完整 EXPLAIN ANALYZE/生命周期标签，不能据此直接判定某一个算子的 CPU 总量错了多少。

### 3.3 物理 IO 桥接把不同阶段都压到同一个带宽上限

| 阶段 | 模型 AP+TP 物理代理速率 (MiB/s) | 同步窗口整设备完成字节 (MiB/s) |
|---|---:|---:|
| S1 | 179.9 | 106.1 |
| S2 | 179.9 | 180.1 |
| S3 | 179.9 | 180.1 |
| S4 | 179.9 | 132.9 |
| S5 | 179.9 | 67.7 |

S2/S3 的设备总吞吐接近不等于每条 AP 的 IO 和 CPU 占比接近。
S1/S4/S5 的“持续满带宽”假设不成立；还缺缓存历史、算子执行阶段及请求节奏。
整设备 IO 包含 TP/后台，不能反推为 AP 或某个算子的精确物理 IO；
本次没有用 miss×常数、旧错位窗口乘2/3、或把未知 AP IO 当0来伪造真值。

发布式 TP hit/miss 计数和数据库驻留页也留了独立时间戳，作为诊断。
它们不是同一 commit 窗口的精确事件真值，不能据此声称“基数推导的额外 SB 已验证准确”。

### 3.4 确定并已修复：漏掉同机 Sysbench 客户端 CPU

旧实现对 `subprocess.Popen(["runuser", ...])` 返回的 PID 直接读 task CPU；
这个 PID 是 `runuser`，真正 Sysbench 在子进程中。S5 以前也只传了基线驱动，
遗漏新增16的客户端进程。

已改为：

- 遍历明确所属驱动根的进程树，所有线程去重计数；
- PID/TID 加 start ticks 识别，成员改变/退出/计数倒退时拒绝相减，不补0；
- S5 两个明确所属驱动根均传入；
- 保留旧 root-only 计数作对照，不篡改历史记录；
- 预测过程无新增复杂回归；这些是离线窗口端点采集，不是在线逐页追踪。

修复后独立 TP128 短测（SB=5.25 GiB，30秒预热+15秒计分）：

- TPS **7969.40**；
- 数据库后端 CPU **221.234秒 / 15秒**，约14.749核；
- 真正驱动进程树 CPU **17.119秒 / 15秒**，约 **1.141核**；
- 旧外壳计数增量 **0秒**；
- 驱动约 **0.1432ms/commit**；数据库后端约1.8507ms/commit；
- 进程树中识别到 `runuser` 与130线程的 `sysbench`；
- 两端 CPU 采样约10.5ms、9.9ms，未靠放宽100ms门限通过。

这说明以16逻辑核为总池却只扣数据库后端，会明显高估 CPU 余量。
修复已覆盖代码路径并真实验证 TP128；修复后的双驱动 S5 与新 TPS 模型仍需独立混跑验证。
不能把单次 TP-only 修复实测当作五阶段新模型验收。

## 4. 按“真值替换，继续检查”的诊断

`diagnostic_audit_current/TPS_DIAGNOSTIC_AUDIT.json` 保存逐层反事实：

1. 原冻结预测；
2. 只替换同 SB TP-only 基线；
3. 再替换 TP-only CPU 成本；
4. 用实测 AP 活跃段 CPU，并单独声明 AP 物理IO为0的反事实边界。

S3 替换基线和TP-only后端CPU后给出约 **7806.6 TPS**，并没有自动接近实测7298.6。
即使加入“实测 AP CPU + 零 AP IO”的诊断，也约 **7681.1 TPS**。
这不是新的预测结果，且“零 AP IO”不是实测真值：它说明只修基线还不够，
CPU共享池范围、阶段CPU服务变化、IO等待仍需一起核对。

未把目标阶段实测 TPS 作为求解器输入，未按S1..S5或查询编号加修正系数。
修复前预测、原始窗口、独立诊断和修复后短测分别保存。

## 5. 已完成 / 尚未解决

**已完成：**

- 真实五阶段连续重叠窗口、同步 commit/device 计数和中间量诊断；
- 新鲜盲计划/元数据，没有续用已失效 Join 统计冒充新统计；
- 修复驱动 CPU 的进程树遗漏及 S5 第二驱动根遗漏；
- 缓存容量桥接明确平尾/容量损失假设，不绕过严格排名拒绝门；
- 回归 **799项**通过，离线审计可在没有数据库的机器重放；
- 实验前后配置字节一致，活动 SB 恢复 **8192 MiB**，实例未重启。

**优先继续补，不宣称已解决：**

1. 刷新 TP128 和真实128+16的独立校准，显式区分数据库后端与同机驱动CPU；
   同机/异机驱动不能共用一个默认CPU范围。
2. 用少数资源段而非整查询平均值预测当前阶段：scan、hash/build/probe、
   spill/merge 的短资源向量即可，保持轻量，不训练查询编号/阶段专属系数。
3. 物理 IO 代理结合缓存状态和活跃段；未知所有权保留未知，不能用整设备总量冒充每查询真值。
4. 再做独立连续轨迹留出验证，并比较6/8 GiB；本轮只有5/5.25 GiB，
   不能证明最佳SB，更不能证明最新最优WM的峰值安全或完整AP完成时间。

本次采样到的全实例动态内存最高约4904 MiB、最小空闲磁盘27.72 GiB、
最小MemAvailable18.60 GiB。它们只是本轮观测，不是查询grant/全生命周期物理峰值验收。
