# AP CPU 竞争层：独立校准与新一轮真实验证（2026-11-16）

## 结论

**这一轮完成了实现、独立校准、16个新目标窗口、逐步真值替换、889项回归和离线精确重放。
但没有得到可以升级默认的冷启动配置推荐模型。**

单一全局“AP占核→TP单位CPU成本膨胀”参数在独立微基准留出上改善了服务成本预测，
迁移到原始复杂Join后却使TPS预测变差，已明确保持opt-in实验状态，不设为默认。
前4秒观测、不加膨胀的在线CPU条件情景对8组均值MAPE为0.89%，但它不是免运行候选配置的预测；
12个配置变化方向也只匹配6个，且AP降幅误差未优于旧口径，不能用小MAPE冒充准确推荐。

## 1. 做了什么

- 保留上一轮独立TP校准，未用本轮目标TPS或本轮TP-only诊断控制重新拟合预测。
- 增加一个全局CPU服务成本参数，无query编号、阶段、SB/WM专用系数。
- 用独立三种扫描/标量聚合微基准及其三种两两组合，测6个训练和6个留出窗口；不是新增12条TPC-H原始查询。
- 训练与留出均在SB=4GiB、TP128下测，三条微基准SQL与目标Q9/Q13/Q18/Q21哈希不重叠。
- 第1轮训练、第2轮反序留出；TP为同一连续驱动，不能声称各窗口有独立TP进程。
- AP占核输入分为AP启动前全查询平均预测和前4秒观测两类；四个事前消融口径全部保留。
- CPU预算闭合显式分离TP-only参考服务与混跑服务，保留同机驱动CPU，不把膨胀后的成本改写成TP-only真值。

独立训练得到：

```text
alpha = 0.019799975356 / AP core
loaded_backend_CPU = reference_backend_CPU * (1 + alpha * forecast_AP_cores)
```

给定留出窗口真实AP占核时，TP后端CPU/commit的留出MAPE：
- 不考虑膨胀：**1.3351%**。
- 加一个独立训练参数：**0.7618%**。

这是“给定AP占核时的服务成本”验证，不是预测AP占核或预测TPS已经合格。

## 2. 新实测协议与全部口径

TP128：只读Sysbench，16×100万行；不是PPT的20GB数据集或真正TPC-C事务。
AP：SF85原始Q9/Q13/Q18/Q21并发，2/4/6/8GiB × LOW/HIGH WM，
每组两次AP重启，次序反转，共16个目标窗口和8个TP-only对照。
AP固定等待15秒后另有前4秒观察，20秒精确提交窗口，实际AP年龄约24.33–26.29秒。
所有口径面对同一批新目标；不是与上一轮7.20%跨批次直接相减。

所有AP仍包有EXPLAIN ANALYZE JSON，CPU/schedstat有自己的100ms边界筛选；
目标TPS来自同一内核窗口提交计数，没有重缩放。没有清缓存，没有验证完整AP生命周期、实际grant或连续PPT五阶段/S5。

## 4. 按要求逐步用真值替换，定位下游

以下全是**离线oracle诊断，绝不是预测准确率**。先保留独立输入，再逐项替换；不会回写预测模型：

| 替换情景 | 16窗口误差MAPE【非预测】 |

| 只把AP占核替换为目标窗口真值，保留冻结TP参考和独立服务模型 | 1.6423% |
| 再替换TP混跑后端CPU/commit，保留冻结TP参考和驱动参考 | 0.4834% |

控制参考情景不重复施加历史AP容量惩罚，仅检查CPU闭合；相邻控制不是严格因果反事实。
代入当前真实参考与全部CPU真值后误差约0.157%，说明本轮剩余问题主要在**输入预测/迁移与执行状态**，
不能说CPU预算公式本身导致了全部误差，也不能把oracle的0.157%当模型成绩。
额外TP物理IO延迟仍未知；全设备读写不等于TP/AP物理归属。

## 5. 找到了哪些具体卡点

1. **TP参考仍会漂移**：本轮冻结TP-only水平相对相邻控制MAPE为1.93%，MAE 182.20TPS。相同boot/二进制不保证性能成本恒定；此次不拿控制窗口事后修正预测。
2. **全程平均占核不是当前阶段占核**：全查询平均AP占核MAE 0.15093核，前4秒条件外推为0.01406核。本批次有改善，不推翻11月14日短探针遇阶段突变失效的证据。
3. **缺CPU排队对AP自身速率的反馈**：补充4秒/proc诊断发现，AP单线程占核约0.10–0.15，运行队列等待比例约0.77–0.85，nice均为0；多数低占核不是单纯IO阻塞。现有静态AP响应主要由全程成本和媒体闭合决定，不能把CPU排队只施加给TP。该诊断只有自己的采样区间，不冒充20秒提交窗口或所有配置的结论。
4. **仅按AP占核的全局TP服务膨胀不够通用**：微基准留出有改善，但复杂Join目标加该项反而变差。访问模式、缓存/访存压力、频率和竞争状态尚未区分；不能据此硬乘系数，或按query编号补偿。
5. **排序还受阶段与噪声约束**：窗口年龄已记录，但不是完整phase matched；若被测均值只差数TPS，当前样本不足以宣称最优。

后续应先补CPU排队→AP进度反馈和当前参考有效性，再用轻量访问强度区分CPU计算与扫描/哈希访存压力；
每项仍需冻结后新验证。不能以本轮不合格参数直接覆盖默认预测。
