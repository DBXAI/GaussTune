## 2. 实现在哪里

新增 `src/jmt/innovation_2_spill/cache_pressure.py`：

1. 读取盲 EXPLAIN、关系页数、实际存储策略；复用创新二预测的扫描量和调用次数。
2. 大表扫描按原生 bulk-read ring 规则计算名义页数，阈值使用**启动 SB**，
   不把在线目标 SB 错当 NBuffers。
3. 同一物理关系的一般池需求去重；重复调用增加访问量，不机械增加独占缓存。
4. 私有 Hash/Sort WM 与 spill 字节不直接计入 SB。
5. 缺失的索引、bitmap、外部访问等语义明确标 unknown，不作为零占用。
6. 输出名义驻留、策略、访问量、未知项；**TP 等效容量损失仍为 null**。

`ForecastSession(..., cache_policy=policy)` 可同时返回原 spill 预测和
`AP_cache_pressure`。不传 policy 时旧输出路径保持不变。

`aggregate_stage_pressure` 汇总阶段的名义 ring/一般池需求。
`retained_page_scenario` 接收执行前缓存状态，给出“无全局淘汰、无 ring 回退”
条件下的驻留情景；不是实际物理上界或统计置信区间。

工具：

- `tools/predict_ap_cache_pressure.py`：冻结 query × WM 和五阶段候选压力计算。
- `tools/test_ap_cache_pressure_live.py`：受限只读实机测试，可做会话级 ring 参数预留对照。
- `tools/replay_ap_cache_pressure.py`：纯标准库离线复核，无数据库与 TTL 续期。

## 3. 第一轮实机测试：25 次真实只读查询

在修改版 openGauss 上，保持共享 SB 为 8192 MiB、默认 ring 为 16 MiB。

测试范围：

- supplier/nation 的小表完整顺序扫描；
- lineitem 的 25 万、100 万、200 万行 LIMIT 扫描；
- orders/customer 的 25 万行 LIMIT 扫描；
- 同一条 lineitem 100 万行查询连续执行三次，检查历史驻留；
- 另外使用**会话级** 32/64 MiB ring 检查策略变化；会话结束/事务回滚后，
  数据库默认值仍是 16 MiB。没有改写全局配置。

每次均先保存盲计划和预测，再执行 EXPLAIN ANALYZE。没有先看目标执行结果再回填预测。
每条语句有 20 秒超时；没有执行完整的大型 AP 查询，没有启动 TP 压测、
重启、调整 SB、清空缓存或修改数据。

### 名义新增 ring 槽位情景的对照示例

下表实测列是主关系**执行前后驻留页的净增量**，不是完整生命周期峰值，也不是 TP 容量损失。
当前池尚有余量，旧页大量保留，因此这些结果只验证当前条件下的局部机制。

| 会话 ring | 受限扫描 | 预测名义 MiB | 实测净增 MiB |
| --- | --- | ---: | ---: |
| 16 MiB | lineitem 100 万行 | 16.000 | 16.000 |
| 32 MiB | lineitem 100 万行 | 32.000 | 32.000 |
| 64 MiB | lineitem 25 万行 | 40.555 | 40.508 |
| 64 MiB | lineitem 100 万行 | 64.000 | 64.000 |
| 64 MiB | orders 25 万行 | 35.969 | 35.891 |
| 64 MiB | customer 25 万行 | 46.742 | 46.648 |

supplier 原本已经驻留 147.531 MiB，重读后仍为 147.531 MiB，而不是再增加一整张表。
这也是为什么驻留量、此次新增量和 TP 等效挤占必须分开。

Shared Read Blocks 是共享缓存未命中计数，不是直接的物理磁盘 IO 真值。
原始实际计划、预测时刻与缓存快照均保留在各 `live_*` 子目录。

## 4. 本轮发现并补上的缺项：旧页跨查询残留

同一条受限 lineitem 查询三次执行前后：

```
88.297 → 104.297 → 120.297 → 136.297 MiB
```

每次名义 ring 是 16 MiB，但旧 ring 页并不会随查询结束而从共享池自动消失。
因此单纯把“当前活跃扫描的 ring”相加，不能预测 AP 累积驻留。

已加入执行前状态的条件情景；真实 TP/AP 全局替换、页间重叠、ring 回退率和阶段残留衰减
仍需后续短窗口校准。不能将上述每次 +16 MiB 无限外推到一个已满且强竞争的缓存池。

## 5. 现有五条 AP、491 个 WM 点的冻结计算

使用既有冻结盲计划及扫描预测，**没有更新或续期旧关联样本**。

| 阶段 | 当前扫描实例/关系集合的名义量 MiB |
| --- | ---: |
| S1 | 64.000 |
| S2 | 275.539 |
| S3 | 371.539 |
| S4 | 435.547 |
| S5 | 371.539 |

这张表不是累积驻留、并发实测峰值或 TP 等效损失；尚未加入来自前阶段的缓存状态。
这些冻结计划在各 WM 下的基表扫描结构一致，因此名义量不随 WM 改变。
**不代表 WM 对实际压力无影响**：它还会改变 spill、扫描持续时间、访问速率或其他查询的计划。

491 个 query × WM 点、65 个阶段/SB 点的公式与计划哈希计算约 1.10 秒。
本轮受限查询的完整创新二预测，预热后通常约 3.5–4.8 毫秒；首次解析/导入约 32 毫秒。
这些不是样本采集、数据库执行或完整生命周期验证的耗时。
