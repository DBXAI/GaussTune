# TPS优化：同机CPU校准与阶段桥接的两轮验证（2026-11-14）

## 结论：修复已保存，候选未通过，不替换默认

旧版已先推送，并加回退标签 **`jmt-before-phase-bridge-20261114`**，对应 `8a82027`。
本轮新增了独立TP校准、显式驱动CPU服务成本、轻量AP预观测、源码/时间戳绑定和两轮真实五阶段验证。

**TP-only校准有改善，但新方案的端到端TPS误差没有优于同轮旧方法，不作为默认推荐模型。**
旧方法也仍未验收，不能因为新候选更差就宣称旧版已准确。

入口：`CURRENT_PHASE_BRIDGE.json`。两轮失败/未达标证据全部保留，不按查询或阶段编号加系数。

## 1. 已实际做了哪些优化

### 1.1 同机CPU记账接通固定点

- TP后端CPU与真正Sysbench进程树CPU分别计数；
  `solve_preview_joint_resources`新增可选的 `tp_driver_cpu_seconds_per_tx`。
- 显式传入时以二者总和检查CPU容量并求解；旧调用不传时标记驱动成本未知，不冒充0已验证。
- fresh calibration只提供实际测过的SB/终端拓扑点，不外推或插值成6/8GiB的结论。
- 校准repeat1提供参数，repeat2只作独立留出；混跑目标TPS不是训练输入。

| 拓扑 | SB (MiB) | repeat1参数TPS | repeat2留出TPS | 相对误差绝对值 |
|---|---:|---:|---:|---:|
| TP128 | 5120 | 7894.27 | 7922.53 | 0.36% |
| TP128 | 5376 | 7902.47 | 7837.13 | 0.83% |
| 原128预热＋新增16首事件门控 | 5376 | 7800.73 | 7821.80 | 0.27% |

TP-only留出平均误差 **0.49%**；没有以平144或缩放TP128冒充S5。

### 1.2 轻量短期桥接，不与冷启动混淆

每个15秒目标窗口之前取4秒AP线程CPU/IO端点观测；预测先保存，目标窗口再开始。
AP当前CPU已受到其IO阻塞影响，不再拿全查询逻辑扫描量把这份CPU二次压低。

- CPU条件预测只用此前AP CPU、独立TP-only校准和原有小固定点。
- task IO保留为提交/记账诊断，不把syscalls当物理IOPS，不冒充完成事件或TP所有权。
- 额外AP物理IO等待尚未建模，结果明确是CPU条件场景，不是已验证的完整CPU/IO模型。
- **这是已有运行信息的短期预测，不是纯计划冷启动预测。**

第二轮15次预测计算平均约 **0.63ms**，最高 **3.40ms**。
4秒是采集等待，不是计算耗时；已有周期观测时纯计算不需要再等4秒。
逐查询端点读取与有界小求解，不引入神经网络、全表统计或在线逐页追踪。

### 1.3 修正预观测与计分窗口的探针条件差异

首轮预观测发生在计数观察器挂载之前，目标窗口则挂载了观察器。
已把预观测钩子移到同一个观察器挂载后、计数窗口启用前；
第二轮逐窗口记录并核对两个条件。探针开销没有乘系数事后“校正”。

两轮执行轨迹/缓存历史不同，不能仅用指标变化量化探针的因果效应；
修复的是条件一致性，不是已隔离证明某个TPS提升。

## 2. 两轮真实测试结果

每轮均为完整原始SF85 AP连续五阶段、每阶段3×15秒窗口。
当前TP为16×1M表的本地readonly负载，不冒称PPT的20GB TP数据。

SB：**5 / 5 / 5.25 / 5.25 / 5.25 GiB**。
WM：Q2=32、Q9=512、Q13=128、Q18=1024、Q21=512 MiB，运行中不改。
这些是较保守固定诊断控制，不是最新spill最优WM；未重新搜索最优SB。

## 3. 剩余误差进一步定位

### 3.1 TP每事务CPU成本不是AP无关常数

第二轮数据库后端＋同机驱动的每事务CPU代理，相对TP-only校准：

| 阶段 | 混跑TP每事务CPU相对上升 |
|---|---:|
| S1 | 1.48% |
| S2 | 1.43% |
| S3 | 2.52% |
| S4 | 3.06% |
| S5 | 2.12% |

这不是用TPS拟合的新系数，而是事后CPU/commit诊断。
可能涉及共享缓存/带宽、执行路径或系统CPU变化，尚未做独立因果隔离。
因此“独立TP-only参数＋AP核数扣减”仍会偏乐观。
不能直接把上述五个百分比按阶段写进模型。

### 3.2 4秒观测不能保证随后15秒处于同一执行阶段

第二轮S4第2窗口，预观测约 **0.75核**，目标窗口AP约 **2.31核**。
第二轮S3第2窗口，预观测约0.51核，目标窗口约1.40核。
数据都可能是各自区间的真实读数，但“保持上一小段状态”的假设错了。
不能把这归结为算子类型覆盖不够；还需要预测阻塞算子/IO与计算段的进度切换。

### 3.3 按真值替换继续检查，仍有误差

独立诊断把目标AP实际CPU替换进去，但仍保留原独立TP校准及“额外AP IO等待未建模”的条件：
第二轮S3/S4窗口平均仍偏高约 **3.06% / 3.69%**。
这说明只修AP CPU状态还不够，TP竞争下的服务成本和额外IO等待也需要补。
该诊断不计入留出预测成绩，不用于重新训练目标查询。

## 4. 版本采用决定与下一步

**本轮新候选不替换默认模型，不授权自动推荐。**
保留确定的CPU采集/显式记账/探针条件修复和实验入口；
新校准、短期条件预测由显式参数启用，旧路径未静默切换。
创新三仍以各SB剩余预算下最小spill为目标，严格混合缓存/物理IO门禁没有取消。

下一步真正需要的是：

1. 用独立、通用的小型AP内存/扫描压力微基准，校准TP服务成本随共享资源竞争的变化；
   不使用这五个query/阶段的误差系数。
2. 从计划中的阻塞边界和可观测进度推导短资源段；
   不能仅以“刚才4秒CPU”代表后续整个阶段。
3. 补TP额外物理IO等待与所有权验证；task IO和整设备完成总量仍各自保留界线。
4. 新输入和方案再次冻结后，用独立轨迹验收；未通过就保留失败，而不是继续在同轮调参。

纯计划冷启动、完整AP时间/spill、所有WM、6/8GiB最优性、算子grant和生命周期物理峰值，
均没有借这次窗口实验宣称已解决。
