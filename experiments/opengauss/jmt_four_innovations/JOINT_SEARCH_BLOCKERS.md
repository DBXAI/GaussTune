## 先纠正上一轮输出

固定 SB=8192、按额外 AP 记账上限最小化逻辑 spill 的表，是一个独立的资源
敏感性候选，**不等于我们的“TP 约束下 AP 延迟最小”的联合推荐**。
不能把“尚未验收”当作一直不跑真正搜索的理由；同样，不能用错窗旧数据、
缺失的 AP 时间/CPU 需求强行填出一个最优 SB。

先补当前有效输入、按明确约束做真实模型搜索，再做独立五阶段混合验证。
不需要等所有部署安全证据都最终验收才开始标定/研究性预测，但预测与验收
必须分开标记，不能跳过单位/窗口/身份真实性检查。

## 真正需要补的工作

### 1. 当前 TP 多 SB 输入 —— 我负责采集/代码，不需要用户手算

- 现有新证据只有 8GiB 下短时事务/设备同窗计数 pilot，不是稳定容量曲线。
- 老 strict 为 3s 事务/约 2s 设备，老 native 为 30s/约29s，不能修 JSON
  或乘比例恢复丢失的绝对边界。
- 需要在多个真实已生效的 SB 点收集同窗事务、cache/设备统计，保留独立重复、
  probe 开销和背景 IO 说明，S5 需要真正的测量期 128+16 拓扑。
- 新轻量 kernel-window 事务证据还没接成完整的正式 TP 输入矩阵，不能把
  现有 legacy native-counter collection 的格式简单改名当成同窗。
- 原 benchmark 账号 `h7v_sysbench` 存在，但密码环境变量当前未设置。
  严格复现原身份时应在本机私密配置凭据，不要在聊天发送密码；
  也可统一采用新实验身份全量重采集，不能混用 peer pilot 与旧角色标定。
  因而凭据不是“算法必须停住”的理由，但实验身份必须明确且一致。

### 2. 复杂 AP 的完整代价与 CPU 接线 —— 我负责修复

- `QueryOption` / `ParetoState` 只有结构内存、IOPS、时间，没有 AP CPU 需求。
- 正式 `pipeline.py -> solve_capacity_tps` 只传 AP 读写 IOPS。
  其他模块有 CPU/并发闭环，但没有接到该正式搜索路径。
- 所以即使输入全部通过旧门禁，CPU 很重、spill 很少的 AP 仍可能被低估。
  不能把这个问题推给磁盘或账号。
- 当前 SF85 全查询没有已验证的新时间/物理 IO 桥接；现有小规模 V3 的
  算子/量级/WM 域不足，不能无检查外推到全查询。
- Q18 HAVING-only SUM 漏算修了，group NDV 仍明显可疑；G=N 是敏感性
  假设，不是新的直接采样统计，不能把假设压力表当成已修复预测。

应补当前直接采样及有代表性算子/查询的离线标定，将 CPU 纳入轻量代价
和联合候选评价。不是继续按查询编号加系数，也不是换成别的优化目标。

### 3. 统一目标和总池 —— 需要明确实验定义

PPT 第27页：TP 为硬约束，达标后最小化 AP 延迟。
PPT 第30页的“TPS 波动控制在10%内”是结果描述，
**没有直接给出最低 TPS 的数值或相对哪个基线的 SLO 定义**。

正式 `objective.select_for_target_tps` 需要数值 target_tps。
旧配置默认 max_tps、手工最小化 spill、或手工固定 SB 都不等价于它。

需要明确最低 Sysbench TPS，或明确相对同并发 TP-only 基线的保护比例。
例如基线90%可作为讨论中的实验阈值，但不能说它已由 PPT 定义或用户确认。

SB 和 AP 还必须共享同一个明示总池，不能延续“SB固定8GiB，AP另给8GiB”
来冒充联合调节。PPT 第19页10500MB为示例，旧模型25559.8MiB为旧机器
标定结果，本次 AP 8192MiB 为策略参数，三者不能混为当前真实预算。

五阶段动态运行还应使用现有 planner/准入状态：运行中查询 WM 保持不变，
不能把五个独立阶段的静态表直接当成可对正在运行 SQL 生效的配置。

### 4. 磁盘 —— 用户可提供帮助，但不妨碍先补 TP 标定

- 本机只有一个 ext4 数据盘，当前约12.1GiB可用；没有找到额外空闲数据盘。
- tmpfs 是内存，不可当成无需内存预算的额外 AP 临时盘。
- 当前条件压力情景的累计临时写量代理约11.2～15.6GiB；
  这是累计写量，不是临时文件物理峰值，更不是实测物理 IO。
- 完整低 WM / 多 AP 混合实验需要更多磁盘余量。建议先准备约50GiB以上
  可用空间作为实验预留，实际需求仍需按临时文件同时存量监控调整。
  该建议不是已证明的安全容量阈值。

## 当前数据规模与 PPT 的区别

本机 `h5_tpcc` 为16个 sbtest 表，每表约100万行，
数据库大小5,104,787,460字节（约5.1GB）；PPT 第29页写 TP20GB。
用当前数据可以获得当前机器的真实搜索结果，但不能保证复现 PPT 的同一
SB 波动/收益。若严格复现20GB，需要另行准备数据与空间，不能悄悄扩表。
