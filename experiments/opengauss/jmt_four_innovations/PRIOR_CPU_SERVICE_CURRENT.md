## 1. 先冻结，再运行

重新独立采集 8 个 TP-only 窗口：2/4/6/8GiB 各两个重复，第一个校准、
第二个留出。本批 TP-only 留出 MAPE=**0.6930%**，没有用混合目标拟合。

然后原始 SF85 q9/q13/q18/q21、LOW/HIGH WM、两次反序重复：

- 8 个 AP-free TP 控制窗，作为未来 AP 窗口的参考，而非这些预测的留出标签；
- **16 个 4 秒先行探针 + 16 个严格后续的 20 秒目标窗**；
- 探针关闭后才创建目标 observer，不同时附加两个；
- 预测先保存，再开始目标窗；探针结束到目标开始间隔 **3.04–3.68 秒**；
- 同时评估“直接沿用先行探针 TPS”的朴素对照，未省略不利结果。

参考预算与加载服务成本严格分开：
`B=纯TP_TPS*(纯TP后端CPU+纯TP驱动CPU)`，
`TPS=min(纯TP_TPS,(B-先行AP占核)/(先行加载TP后端CPU+先行驱动CPU))`。
没有查询编号系数、目标 TPS 缩放或旧 alpha 回灌。

## 4. 问题已经定位到哪里

不是单纯“算子种类写少了”，也不是多加一个全局倍数能解决。
目前链路里仍有两个未可靠预测的未来输入：

1. **AP 的阶段进度**。全查询 CPU/全查询时间不能直接代表未来 20 秒占核；
   单个短窗观测也未必能延续。
2. **该阶段下 TP 的单位 CPU 成本**。纯 TP 成本和加载成本不同；
   先行加载成本也会随接下来的 AP 阶段改变。

现有采集能证实未来资源状态改变，但尚不能分离具体算子切换、缓存、
调度或实际 grant 各自的贡献。运行队列统计不是算子进度真值，
不能声称已经确认是哪个 Hash/Sort 算子的计算公式有错。

反例：SB4GiB+LOW，重复1：

- AP：先行 **0.4198 核 → 后续 1.0091 核**；
- TP 后端：先行 **1.5515ms/事务 → 后续 1.6386ms/事务**；
- 完整 CPU 预测误差 **9.96%**，朴素 TPS 误差也达 9.47%。

反向也存在：相同配置重复2，AP 从 1.4712 核降到 0.9383 核。
因此不能给这一查询/配置固定乘一个校正系数。

全批先行估计对未来的误差：
AP 占核 MAE=**0.3534 核**，TP 后端单位 CPU MAPE=**2.2949%**，
驱动单位 CPU MAPE=1.3917%。队列公式不能补回这些阶段输入误差。

下一步真正需要补的是轻量**算子流水线/阶段进度**：
复用创新二的 CPU 工作量、扫描与 spill 估计，按 Hash build、Sort、
阻塞聚合等边界拆阶段，再推未来窗口各阶段占比与 TP 服务成本。
目前没有实现/验收这一阶段模型，不能把设计方向写成已解决。
实际 grant、query-owned 完整物理 IO、连续五阶段仍是独立未验收项。
