# PPT 实验一（Sysbench）定向检查

日期：2026-11-11。**只检查实验一：Q18 → Q18/Q21 →
Q9/Q13/Q18/Q21 → 再加 Q2 → 去掉 Q2、TP 从 128 增至 144。**

## 结论

当前模型能够运行算子工作量计算，能够区分部分查询差异，
但**尚不能准确推荐完整五阶段，也没有可靠地产出
8192→4096→4096→4096→8192 MiB 的 SB 序列**。
这不是仅因缺少验收手续：本次找到实际计算遗漏、统计失真风险和资源耦合缺失。
不能通过阶段编号指定 SB，也不能以是否画出波形作为准确性标准。

## 本次实际做了什么

- 对照原实验 AP bundle，核对五条真实 SQL 的 SHA-256，无派生 SQL 替换。
- 使用本机 `h5_tpch` SF85 数据库，而非之前的 SF10 校准库。
- 对每条查询采集 WM=64/512/1150MiB 的只读 EXPLAIN，共 15 点。
- 没有执行目标查询、ANALYZE、TP 负载、重启或全局参数修改。
- 用冻结 V3 算子模型计算结构工作量，再用隔离候选回放相同盲计划。
- 历史执行记录仅用于单独的问题诊断，未进入本次预测输入。

原始证据位于：

`/root/JMT_SAMPLE_NEXT_20261111/results/sysbench_experiment1_20261111/plans_1715/`

## 一、现在确实漏掉了 AP 复杂度：Q18 的 HAVING-only SUM

当前 Q18 内层聚合的 VERBOSE 计划：

```text
Output: lineitem.l_orderkey
Filter: sum(lineitem.l_quantity) > 314
Child: Seq Scan, Plan Rows ≈ 510,081,248
```

旧模型只在 Output 识别聚合函数，因而：

- 内层 SUM 的聚合转移次数为 **0**；
- 相应的 SUM 转移状态内存和部分 CPU/表达式类型信息也遗漏。

候选修复统一收集 Output 与 Filter 中的聚合状态并去重，
使内层 SUM 的工作量变为 **510,081,248 次计划输入行上的转移**。
这是工作量正确性修复，不是新测得的真实行数或时间准确率提升。

只修改四个通用模块：

1. `innovation_2_spill/ap_plan_model.py`：统一聚合识别、状态/工作量计算；
2. `innovation_2_spill/ap_expr_types.py`：HAVING-only 参数类型与内部排序信息；
3. `innovation_4_performance/ap_cpu_features.py`：HAVING-only numeric 工作量；
4. `innovation_2_spill/diagnostics.py`：事后诊断中区分 pre-/post-HAVING 分组数。

候选回放的 15 点中，仅 Q18 的资源特征发生变化；其他四条 SQL 的资源特征未变。
原冻结 V3 代码未改动。310 个原核心测试、29 个成本/CPU 回归测试、
14 个新增测试，共 **353 个测试通过**。

## 二、SF85 的分组输入依然不足：HAVING 之前的 G

当前目录 `lineitem.l_orderkey` 的 NDV 为 **363,490**，
当前 Q18 结构模型内层聚合也据此只保留约 36.35 万组。

历史原 SQL 执行记录（不是本次的新执行）：

- HAVING 后 `Actual Rows = 641`；
- `Rows Removed by Filter = 127,499,359`；
- `Actual Loops = 1`；
- 所以 HAVING 前状态数为 **127,500,000**，约为当前目录 NDV 的 **350.77 倍**。

这说明该统计输入存在非常大的失真风险；不能把 HAVING 后输出或未经验证的
目录 NDV 当作可靠的建表 G。历史值没有注入当前预测，也没有给查询编号设置系数。

**本次只补聚合识别，不声称修好了 SF85 的 G 或 spill 准确率。**
下一步须为 SF85 补合格的轻量直接采样/关联统计，并验证 HAVING 前分组数。

## 三、严格五阶段链没有接收 AP CPU

实际代码检查：

- `QueryOption`：WM、动态峰值、读/写请求数、执行时间、计划族；
- DP 状态：内存、读/写 IOPS、执行时间；
- `solve_capacity_tps()`：TP 缓存比例、TP 请求数、AP 读/写 IOPS、
  设备服务时间/延迟曲面；**没有 AP CPU 工作量或 CPU 容量输入**。

另有 AP CPU/并发闭环组件，但当前严格五阶段候选/DP/TPS 调用链未接入它。
因此 AP 的 CPU 复杂度没有作为独立资源维度进入 TP 吞吐预测；
相同 IO/内存条件下，单纯增大 AP CPU 工作量不能通过这条路径影响 TP。

这使得“增加 WM 后 spill 减少，但 AP 更快占用 CPU、反而影响 TP”的权衡不完整，
也使 S5 增加终端后的 CPU 饱和问题无法被这条路径充分解释。
单独补更多算子名字，或者继续细调 spill 公式，不能解决这个接口问题。

## 四、五条查询应分别看到什么

以下来自真实 EXPLAIN 的结构，不是实测资源真值：

|查询|本次计划节点数|不能忽略的主要复杂度|
|---|---:|---|
|Q2|32|子查询被改写成多层 Hash Join/Semi Join；少量输出不等于少量扫描/探测|
|Q9|20|多表连接、Merge Join、大排序和 Materialize；不仅是 Hash spill|
|Q13|8|外连接和两层聚合；节点少，但中间基数/分组状态可能很大|
|Q18|14|全表聚合、HAVING 前状态、再连接和最终聚合；本次发现隐藏 SUM 漏算|
|Q21|19|lineitem 多次扫描、Semi/Anti Join、同键候选比较和过滤相关性|

当前 V3 时间标定未覆盖 Q9 中 Merge Join/Nested Loop/Materialize 的成本域，
且 SF85 多项工作量远超其 SF10 标定范围。不能拿之前四条小查询的误差
当作本表五条查询的准确率。

## SB 波动应该怎样得到

- S1：在 TP SLO 满足的条件下，为 Q18 分配有收益的动态内存；
- S2/S3：新 AP 的实际动态内存、IO 与 CPU 需求改变可行域；
  若让出 SB 给 AP 能降低总竞争且仍保护 TP，搜索应自然选较小 SB；
- S4：超出可行域时由准入/排队控制，不能假装五条查询都能同时满足预算；
- S5：TP 128→144 后重新算 TP 缓存收益和 CPU/IO 竞争；
  只有增加 SB 确实改善 TP 且 AP 预算可行，才应回升，否则应调整 AP 准入。

所以 SB 序列**可以有波动，但不能预设必须波动**。
当前缺口使我们还不能可靠算出上述权衡，更不能宣称复现 PPT 效果。
目标是验证预算和 TP SLO 下的收益，而不是拟合五个 SB 数值。
