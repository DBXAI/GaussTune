## 2. 轻量计算方法

对顺序扫描，设基表估计总行数 N、目录页数 P、每次调用实际要扫描的预估行数 n：

```
预计访问页数 ≈ min(P, n × P/N)
名义 ring 驻留页数 ≈ min(预计访问页数, 原生 ring 页数)
```

这里 n 是 LIMIT/调用次数修正后的**过滤前基表扫描行数**，不是 Join、Group By
或 WHERE 输出基数。完整 Seq Scan 即使只输出 1 行，也仍可能扫描全部基表页。
Hash/Sort 执行内存和 spill 文件没有算进 SB。

阶段中，一般池的同一物理关系去重；不同私有 ring 按各自实例计数。一次执行里的
rescan 不等于新建一套 ring。若给定执行前 AP 缓存状态，则另计算旧页保留/新页
重叠的条件情景。没有实际页面集合时不伪造重叠精度。

最后使用尚待混合校验的轻量近似：

```
共享 SB 容量提示 = TP-only 参考容量 + AP 条件驻留量
```

AP 驻留不一定等于 TP 的等效容量损失，因此结果只能作为软容量/验证候选；
不能作为混合 miss 曲线的硬剪枝，更不能自动成为 TPS 最优配置。

## 4. 为什么改进 Join 基数后未必得到大几个 GiB

此次五条计划都以大表 Seq Scan 为主，bulk-read ring 已被扫描行数充分填满。
更大的 Hash Join 中间结果会增加私有内存/spill/CPU，但不会直接多占等量 SB。
在扫描路径固定的情况下，将非扫描算子的输入/输出行数乘 0.5/1/2，名义缓存量不变。

所以 6/8 GiB 比较更好的现象不能仅靠“Join 结果大”解释。后续要核对：
一般池替换、历史页残留、扫描速率、TP 热页复用，以及 OS cache/物理 IO 竞争。
当前模型没有偷偷把这些未知量补成查询专属系数。

## 5. 新的实机验证：6 条受限只读查询

所有预测都先保存，再执行 EXPLAIN ANALYZE；没有用 Actual Rows 回填输入。
SB 一直为 8 GiB、默认 ring 16 MiB，未清缓存、重启、启动 TP 或执行完整大查询。

| 查询 | 基数换算预计页访问 | 实测共享页访问 |
| --- | ---: | ---: |
| lineitem LIMIT 1000 | 20.763 | 21 |
| lineitem LIMIT 50000 | 1038.136 | 1038 |
| lineitem LIMIT 750000 | 15572.044 | 15575 |
| orders LIMIT 50000 | 920.740 | 921 |
| customer LIMIT 50000 | 1196.491 | 1199 |
| supplier 过滤后仅约 1 行的 Seq Scan | 18884.000 | 18884 |

这 6 点的页访问加权绝对误差约 **0.0162%**，仅验证平均行/页换算在这些顺序扫描上的效果。
Shared Read 是 SB miss，不是物理磁盘 IO。

不准确/未验证之处也保留了：

- 访问页数不是新增驻留页数。例如 LIMIT 1000 访问 21 页，但驻留净增仅 13 页，
  因为其中一些页已经在缓存中。
- supplier 过滤输出很小，但仍访问 18884 页；旧页已驻留，所以净增 0。
- 未测 TP miss 增量，未证明“驻留 MiB = TP 等效损失 MiB”。
- 索引/bitmap/并行域仍明确 unknown，不补零。
